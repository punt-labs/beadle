02The four documented invariants

docs/ARCHITECTURE.md lists these as design invariants. Three hold. One is a claim with no code behind it.

InvariantStatusReality
Zero agent authority
every executed command is signed		 partial True for execution. But OnNewMail creates the mission record and starts the pipeline goroutine on trust + permission alone, with no signed command in that decision. With zero commands loaded nothing downstream runs, so it is currently harmless — the record is still created unconditionally. Documented in ARCHITECTURE.md as a known gap.
Preflight before execute real Args validated before any command runs; no partial execution.
Isolated verification real Inbound and recipe signature checks each run in their own temporary GNUPGHOME. An untrusted key never touches the system keyring.
Expired / non-expiring keys rejected real Enforced on the primary key and any signing-capable subkey.
Audit log is tamperproof
append-only, GPG-signed		 absent There is no audit log. Grep for it in internal/daemon returns four comments mentioning the word and zero implementation. The pipeline records added this week are operational state, not a signed audit trail — they are mutable and unsigned. beadle-623.

The one to be honest about

A document promising a tamperproof, GPG-signed, append-only audit log, with nothing behind it, is worse than silence: it invites someone to rely on a control that does not exist. Either build it or move the claim out of the invariants list and into a roadmap. Both are fine; leaving it as an invariant is not.

03Can a new operator actually use this?

No. This is the largest practical gap and it is not a code defect.

A fresh install runs zero commands, by design, with no way out

The daemon refuses to load recipes unless ~/.punt-labs/beadle/daemon.json names an authorizer key and each recipe carries that key's signature. That default is correct — it is the zero-agent-authority posture.

But no tooling exists to reach the configured state. There is no beadle init and no beadle sign in either binary — verified. An operator must hand-write daemon.json, then hand-craft a canonical-subset signature over each recipe by replicating what internal/daemon does internally. In practice that means the daemon is operable by someone who reads the source. Tracked as beadle-7gm.

The tier's best evidence is that it caught its own bugs

Within minutes of first running in CI it found three violations of its own premise: a symlink to the developer's global archetypes tree, make test not putting the installed binary on PATH, and a GOPATH expression that breaks on multi-entry values.

None were findable from the authoring machine, because that is precisely the environment in which none of them reproduce. For a change whose whole premise is dev/CI parity, local validation was the weakest available signal. Recorded as DES-036.

05The path to real

Ordered by what unblocks the most, not by size. The first two are the difference between "a developer can demo this" and "an operator can run it."

  1. Make the trust story honest — beadle-hv7i (P2) Verify IMAP is loopback before honoring Proton-origin headers, or refuse to classify as Trusted. Right now one of the two accepted trust levels rests on an unverified environmental assumption that the code itself flags. Cheapest security fix on the list, and the test tier makes the negative case easy.
  2. Give an operator a way in — beadle-7gm (P3, misprioritized) beadle init and beadle sign. Without these the daemon is unusable by anyone who has not read internal/daemon. This is P3 and should not be; it gates every other daemon capability from a user's perspective.
  3. Close the trigger gap — beadle-ivtd (P3) Assert that the daemon's real wiring produces a plan for a representative email. Keep the harness's stub planner — that separation is correct. This is separate coverage, not a change to the tier.
  4. Resolve the audit-log claim — beadle-623 (P3) Build it or demote it out of the invariants list. An unimplemented invariant is a liability in a document people are told to trust.
  5. Cover the persistence wiring — beadle-fbhp (P2) Now cheap: the fixtures exist. Pass a real store into the harness and assert a record reaches disk. Then remove the wiring line and confirm the test fails.
  6. Decide on worker sandboxing — unfiled spawner.go:109's container-isolation TODO has no bead. The worker runs with a narrowed env and PATH but no namespace or seccomp confinement. Either file it with a decision or record why the current confinement is sufficient.
  7. Then, and only then, LLMPlanner — beadle-tl6 (P3) Letting trusted mail author a plan removes the "it can only pick from pre-signed recipes" safety property. It needs its own authorization story, and it should land after the trust and audit gaps above are closed rather than before.

One thing this artifact is not

A verdict on beadle-email. That path — an agent with a mailbox, reading and replying under r/w grants — has real usage behind it and works. Everything above is about beadle-daemon, the x-gated recipe runner, which had been exercised about three times before this week. The two share a trust model and almost nothing else.
