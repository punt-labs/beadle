Beadle: what it can do, and why you can trust it

Beadle gives an AI agent its own email address. This is about that mailbox — not yours.

Whose mailbox is this?

Beadle isn't a tool that reads a person's personal inbox. It gives an autonomous agent (say, claude@punt-labs.com) a mailbox of its own. Email becomes a channel people can use to send that agent instructions — from anywhere, without a live session. That's powerful, and it's exactly why it needs a real trust model: anyone who can get a message into that mailbox is, in some sense, talking directly to the agent.

Two checks decide everything the agent does

Every message shows up with its verification rung — check 1 always runs and needs no grant from anyone. Check 2, the permission grant, is what decides everything past that: without r, a sender's message appears with its subject redacted and can't be opened at all. Hold r and it opens; hold w and the agent can reply to it; hold x and it can trigger a recipe. Nothing happens without an explicit grant for it:

1

How well-verified is this message?

Can the claimed sender actually be proven — or could anyone have written that "From:" line?

2

What has this specific sender been granted?

Being verified isn't enough on its own — the sender also needs an explicit grant for whatever they're asking the agent to do.

Check 1 — how well-verified is this message?

Every message lands on one of four rungs, based on how hard it would be to fake:

🔒
Sealed
Sent Proton-to-Proton, end-to-end encrypted. Could not have been forged in transit.
✍️
Signed & checked
Digitally signed, and the signature actually checked out against a known key.
⚠️
Signed, but broken
Claims to be signed, but the signature is invalid — a red flag, possible impersonation.
📨
Plain mail
No signature at all. As trustworthy as an unsigned letter — which is to say, not very.

Check 2 — what has this sender been granted?

There is no privileged "owner" role that sits above everyone else. Power to direct the agent comes entirely from grants set per sender, on a per-mailbox basis:

r
Read — the agent may look at this sender's mail and pay attention to it.
w
Write — the agent may reply to this sender.
x
Execute — this sender's mail may trigger an automated task, not just a reply.

Any number of different people or systems can each hold their own combination of these, completely independently — a teammate might have rw, a monitoring bot might have only r, a CI system might have x. Nobody is special by default; a sealed, perfectly-verified message from someone with no grant at all still unlocks nothing.

Passing both checks: two very different things can happen next

What actually varies isn't who's watching — it's what kind of action a grant unlocks:

r / w — judgment

The agent reads it and decides

Once a message clears both checks, its content becomes something the agent actually reasons about — it reads what the sender is asking and decides how to respond, using judgment, the same as if someone had typed the request straight into a session with it.

x — fixed recipe

A pre-signed recipe runs

The background daemon works differently: a verified, permitted email doesn't get to freely instruct anything. It can only pick which of a small set of recipes runs — recipe files that were written and digitally signed in advance. The email supplies no new instructions, only a selection.

Who's allowed to sign a recipe is a separate question from who holds x. Each running daemon has exactly one configured authorizer — a specific GPG key that every recipe file must be signed with before the daemon will load it at all. Holding x on a contact only lets that sender's mail select among the recipes the authorizer already signed; it grants no power to write new ones. And the reverse holds too — being the authorizer doesn't grant any rwx permission over anyone's mail; it only decides which recipe files are real. These are two independent locks, not a hierarchy.
Why the recipe needs that extra lock at all. Reading a message and using judgment has a safety net built in — the agent can notice something's off. Running a fixed recipe has no such net: it just executes, exactly as written. So a recipe file needs a signature check that has nothing to do with any individual email being trustworthy — it's checked once, at load time, against the one key configured as this daemon's authorizer. Skip that setup entirely and this path does nothing at all, rather than guessing at what's safe. A daemon that's configured with an authorizer key but can't actually resolve it refuses to load any recipe, never "run it anyway."

For the technically curious

Check 1 = the four-level classifier (trusted/verified/untrusted/unverified), backed by PGP signature verification and Proton's end-to-end headers. Check 2 = the per-contact rwx bits (contacts.CheckPermission) — a plain lookup with no special-cased identity, so any number of contacts can independently hold any combination. The authorizer concept is currently named owner_handle/owner_gpg_key_id in daemon.json and ownerKeyID through internal/daemon's code — that naming is being corrected to "authorizer" (tracked as beadle-4ul) because "owner" wrongly implied a general position of authority that doesn't exist anywhere else in the system. The mechanism itself, VerifySignature gating beadle-daemon's command loader (DES-034/035), is unaffected by the rename — only the name is wrong today, not the design.
